# Known Technical Debt — Governance Operations

Recorded per DEBT-020 while hardening the engine (PR #4). Owner: engineering governance maintainers.

| DEBT-GOV-001 | RESOLVED. The CLI cast the governance pack without schema validation and crashed on malformed packs. | Uncontrolled crash on malformed packs. | Resolved on main (PR #1): the CLI validates the pack against the schema and the engine rejects semantically invalid packs, exiting with a diagnostic. |
| DEBT-GOV-002 | PARTLY RESOLVED. Exceptions are evaluated (scope, metadata, time window, requester must differ from approver). An approver-authority policy (`model/authority/`) now models EXC-021 section 15's roles by severity, and the engine lets a P1 waiver or P1 risk acceptance hold when the approver holds an APPROVED role that covers it. P0 never holds. Every role in the v0.1 policy is DRAFT with unassigned holders, so nothing is enforced yet and P1 waivers still do not hold. | P1 waivers still blocked until roles are approved. | Leadership approves roles and names holders (and settles the EXC-021 versus blueprint conflict over who approves P1). Remaining gap: this is opt-in, and risk acceptances are still a claimed identity that is not authenticated. Not modelled: the additional security authority and PRD-018 visibility (EXC-021 section 15). |

| DEBT-GOV-009 | A WARN tool result maps to `PARTIALLY_VERIFIED`, which the engine does not accept as proof of a control, so a control linked to WARN evidence is UNVERIFIED and blocks (NO-GO), although the WARN definition says "non-blocking". | DEBT-GOV-010 | PARTLY RESOLVED 2026-11-19. The three adapters now replay output captured from the real tools (osv-scanner 2.7.1, gitleaks 8.30.1, semgrep 1.186.0, run on a GitHub Actions runner; `analyzer/tests/fixtures/real-scanner-output`). Every field the parsers read and every exit code they assumed was confirmed, with two differences, both fixed: `gitleaks git` in a directory that is not a git repository logs an error and exits 0 (the adapter would have reported a clean history), and `osv-scanner --version` prints four lines (the first is now used). osv-scanner's `database_specific.severity` label exists on GitHub-reviewed advisories and each group also carries a CVSS score; the adapter now uses the worse of the two and assumes P1 only when neither exists. Still open: the fixtures are tiny, so behaviour on a large repository, a monorepo, a proxy, Windows path forms and the 2 MB output buffer is unobserved. osv-scanner cannot tell runtime from development dependencies and the advisory-data date is not recorded. Gitleaks findings carry no file or line by design, and a shallow clone limits the history scanned. Semgrep inline `nosemgrep` suppressions cannot be counted, and no rule set exists in any repository, so the check is UNSUPPORTED everywhere. All three resolve the tool through `PATH` (whether a binary planted in a scanned repository could be picked up on Windows is unchecked), and the runner does not forward proxy variables. | Possible false P1s or ERROR on large real repositories; reduced evidence of data freshness; untrusted-repository exposure not assessed. | Run the adapters on this repository and one large one and capture the output; record the advisory snapshot; author a reviewed Semgrep rule set; check executable resolution for untrusted repositories; revisit proxy handling and buffer size. |

| DEBT-GOV-012 | The Claude Code plugin (`plugins/engineering-governance`) is only partly verified in a live session. `validate` and `check` were seen running from an installed plugin on a real project (user-reported output, 2026-11-18), which confirms `${CLAUDE_PLUGIN_ROOT}` substitution and the shell injection. Not yet seen live: `analyze`, `report`, `init`, `setup`, `review`, and option pass-through through `$ARGUMENTS` (for example `--base`). Installing through the desktop app creates a synced plugin that Claude Code sessions do not load; it must also be installed with `claude plugin install`. The committed `bundle/governance.mjs` is a generated artifact (a freshness test guards it) built with esbuild 0.28.2, whose install script is not approved under npm's allowScripts policy (the bundler works without it). The repository is under a custom license (`LICENSE`: use and modify for own use, no redistribution), which is not OSI open source and has not had legal review; its text was drafted from the owner's stated terms without legal advice. The bundle is not signed or provenance-attested. | A command or option may still fail where it has not been seen; the licence needs a lawyer's read before reliance; the bundle's provenance rests on the repository alone. | Run the unseen commands and an option such as `--base` once in a live session and fix any problem; have the licence reviewed, in particular its no-redistribution clause against how adopters copy templates and fork on GitHub; decide on release tagging and provenance before publishing. |
| DEBT-GOV-013 | `/engineering-governance:setup` has Claude draft governance packs and record evidence from checks it runs (ADR-0002). The CLI verifies that a pack is internally consistent (evidence status not stronger than `result_status`) but cannot verify that a command was really run, that the exit code is real, or that a check covers the control it is attached to. Packs are marked unreviewed. `setup` has not been run in a live Claude Code session. | A mis-recorded check could make a control look verified; drafted controls reflect the model's reading of a repository. | Review packs in a pull request and re-run the recorded commands. Preferred fix: have the CLI run declared checks and write the evidence itself (the tool-collected option in ADR-0002), after DEBT-GOV-009 is settled. |
| DEBT-GOV-014 | `/engineering-governance:review` has Claude read one area of a repository against the standards and add findings to the pack (ADR-0003). It is not exhaustive: a large repository cannot be read in one pass, so coverage is a sample that the report must state, and the model can be wrong or miss things. The CLI checks a finding's shape and that it cites existing evidence, not that its quoted code, line or reasoning is correct. An open P0 or P1 finding blocks `check` until a person sets it `RESOLVED`, so a false positive blocks until dismissed and there is no status for "reviewed and rejected". The command has not been run in a live session. | False positives may block a decision; false negatives give false comfort; findings cite code that may have changed. | A person confirms each finding before acting. Consider a distinct status or exception path for rejected findings, and a deterministic check that quoted code still exists at the cited line. |
| DEBT-GOV-015 | `governance summarize` flags a "possible gap" from directory names and scripts (`migrations/`, `contracts/`, `tests/`, a test script, CI workflows) and maps a control to an area only through its standard id, so a control filed under another standard, or an area with no signal, is missed or mis-shown. The area list is a constant kept equal to the plugin's `review-areas.json` by a test. The `/engineering-governance:summary` suggestions are AI-written and not verified, and the command has not been run in a live session. | A gap can be missed or over-reported; suggestions can be wrong. | Treat the flags as prompts; add more signals as real repositories show what is missing; review suggestions before acting. |
| DEBT-GOV-016 | `/engineering-governance:audit` has Claude document a repository and review each area in turn, then write an entry report with a prioritized plan (ADR-0004). It is slow and token-heavy, each review reads only a sample of its area, and the plan is the model's synthesis of the area reports, not a computed result. It relies on subagents (one per area, run sequentially because they all append to one pack) and on Claude following long instructions; if the Agent tool is unavailable it does the areas itself. Files it writes are never overwritten, but Claude's Write tool, not the CLI, creates them, so the never-overwrite rule rests on the instructions. It has not been run in a live session. | A long run may stop partway or skip detail; the plan can mis-prioritize or omit things; the reports quote real code. | Review the reports before committing and before acting. Preferred fix: have the CLI own file creation for every report and assemble the index mechanically from the area reports. |
| DEBT-GOV-017 | The assessment history (`.governance/history/assessments.jsonl`, OPS-01/02) is hash-chained, which detects an edited, removed or reordered record in the middle, but not: deleting the newest records (the shorter chain is still valid), or someone with write access recomputing the whole chain. It is unsigned and has no external anchor; `--record` is opt-in, so a check that is not recorded leaves no trace; two writers recording at once to one checkout can claim the same sequence number (the next read reports the break); the store is one growing file with no retention rule; a "resolved" issue only means it was absent from the next recorded assessment, not that remediation evidence was accepted; the store records the fact set, not the full report. | The history is tamper-evident against careless edits, not tamper-proof against a determined one. | OPS-05: sign records or publish the latest hash somewhere the writer cannot rewrite (a tag, CI artifact or ticket); decide retention and access; consider recording by default in CI. |
| DEBT-GOV-018 | Exception lifecycle and signed approvals (OPS-03). Signing uses GnuPG only; Sigstore (keyless, identity-bound signing) is not implemented. Verification is opt-in (`--verify-signatures`); without it a declared approver is still trusted, and the report says so. A signature is accepted when GnuPG reports a good signature (GOODSIG and VALIDSIG) from a key whose fingerprint is registered for the named approver in the authority policy; the web of trust and key trust levels are not consulted, and revocation or expiry is only as current as the verifier's local keyring. The authority policy is itself a file in the repository: anyone who can change it and the pack can register their own key, so the policy needs protected-branch review (CODEOWNERS). Only exception approvals are signed; risk acceptances and decision records are not. Renewal overwrites the signature file, so earlier approvals survive only in git and the assessment history. There is no maximum exception duration (EXC-021 may set one) and `exception expire` is a command someone must run, though an expired exception stops holding at evaluation time regardless. Approvers are matched by name or handle. | A repository admin who controls both the policy and the pack can still forge an approval; an exception approved without `--sign` is trusted as declared. | Add Sigstore, sign risk acceptances, enforce a maximum duration from the standard, protect the policy file with CODEOWNERS, and make `--verify-signatures` the default in CI. |
| DEBT-GOV-019 | The pull-request comment and production-approval workflows (CI-03, CI-04) have never run on GitHub. They are checked statically (pinned action SHAs, no `pull_request_target`, permissions, wiring) and the comment text and posting logic are unit tested, but the Actions runtime, artifact hand-off between the check and comment workflows, and the approvals API response are unverified until a first real run; `download-artifact` is pinned to v7.0.0 on the assumption it pairs with `upload-artifact` v7.0.2. The approval gate depends on repository settings (required reviewers, prevent self-review, branch restriction) that no workflow can create or enforce; the job fails when it sees no recorded approval, which catches an ungated environment but not a reviewer list that includes the requester. The approval record is a workflow artifact, not tamper-evident (compare DEBT-GOV-017). A reviewer's approval comment is written unescaped to the job summary. The scenario matrix covers the four outcomes through `check`; it does not run the GitHub workflow. | A first run may need fixes; a misconfigured environment weakens the release gate. | Run both workflows once in a scratch repository, then pin them in a release tag; protect the `production` environment and review its settings periodically; consider writing the approval record into the assessment history. |
| DEBT-GOV-020 | Evidence integrity (EVD-05). The repository fingerprint covers file paths and the content of source files and manifests (including lockfiles) only; a change to any other file (CI workflows, SQL, configuration, documentation) does not change it, so evidence bound to a fingerprint stays usable after such a change. It reads the working tree, so uncommitted edits change it while the recorded git `head` does not. Evidence is bound only when it names a `repository_fingerprint`: pack evidence that names none is never invalidated by a code change, and evidence produced by the CLI always carries the current fingerprint, so only hand-saved or carried-over evidence is affected. The fingerprint algorithm changed (v1 to v2, length-prefixed) and the history records it from now on, so a fingerprint saved by an earlier build never matches; there is no command yet that re-runs an assessment and compares it with a recorded one (`governance history` shows the fingerprints, nothing verifies them). `.governance/history/` and `.governance/reports/` are excluded from the fingerprint by path, so a change to a file there is invisible to it. Reproducibility tests normalise wall-clock fields (`generatedAt`, `assessmentId`, `evaluatedAt`, `generated_at`, `duration_ms`); verification tools that report different results over time (an advisory database, a scanner version) are outside what they prove. | Evidence can outlive a change to a file the fingerprint does not read; a recorded decision cannot yet be mechanically re-verified. | Widen the fingerprint to every tracked file (a git tree hash is the obvious source), add `governance verify <n>` to re-assess a recorded head and compare, and record tool and advisory-data versions with the evidence. |
