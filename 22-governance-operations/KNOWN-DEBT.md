| DEBT-GOV-010 | PARTLY RESOLVED 2026-11-19. | DEBT-GOV-017 | The assessment history (`.governance/history/assessments.jsonl`, OPS-01/02) is hash-chained, which detects an edited, removed or reordered record in the middle, but not: deleting the newest records (the shorter chain is still valid), or someone with write access recomputing the whole chain. It is unsigned and has no external anchor; `--record` is opt-in, so a check that is not recorded leaves no trace; two writers recording at once to one checkout can claim the same sequence number (the next read reports the break); the store is one growing file with no retention rule; a "resolved" issue only means it was absent from the next recorded assessment, not that remediation evidence was accepted; the store records the fact set, not the full report. | The history is tamper-evident against careless edits, not tamper-proof against a determined one. | OPS-05: sign records or publish the latest hash somewhere the writer cannot rewrite (a tag, CI artifact or ticket); decide retention and access; consider recording by default in CI. |
| DEBT-GOV-018 | Exception lifecycle and signed approvals (OPS-03). Signing uses GnuPG only; Sigstore (keyless, identity-bound signing) is not implemented. Verification is opt-in (`--verify-signatures`); without it a declared approver is still trusted, and the report says so. A signature is accepted when GnuPG reports a good signature (GOODSIG and VALIDSIG) from a key whose fingerprint is registered for the named approver in the authority policy; the web of trust and key trust levels are not consulted, and revocation or expiry is only as current as the verifier's local keyring. The authority policy is itself a file in the repository: anyone who can change it and the pack can register their own key, so the policy needs protected-branch review (CODEOWNERS). Only exception approvals are signed; risk acceptances and decision records are not. Renewal overwrites the signature file, so earlier approvals survive only in git and the assessment history. There is no maximum exception duration (EXC-021 may set one) and `exception expire` is a command someone must run, though an expired exception stops holding at evaluation time regardless. Approvers are matched by name or handle. | A repository admin who controls both the policy and the pack can still forge an approval; an exception approved without `--sign` is trusted as declared. | Add Sigstore, sign risk acceptances, enforce a maximum duration from the standard, protect the policy file with CODEOWNERS, and make `--verify-signatures` the default in CI. |

The scenario matrix covers the four outcomes through `check`; it does not run the GitHub workflow. | A first run may need fixes; a misconfigured environment weakens the release gate. | Run both workflows once in a scratch repository, then pin them in a release tag; protect the `production` environment and review its settings periodically; consider writing the approval record into the assessment history. |
| DEBT-GOV-020 | Evidence integrity (EVD-05). The repository fingerprint covers file paths and the content of source files and manifests (including lockfiles) only; a change to any other file (CI workflows, SQL, configuration, documentation) does not change it, so evidence bound to a fingerprint stays usable after such a change. It reads the working tree, so uncommitted edits change it while the recorded git `head` does not. Evidence is bound only when it names a `repository_fingerprint`: pack evidence that names none is never invalidated by a code change, and evidence produced by the CLI always carries the current fingerprint, so only hand-saved or carried-over evidence is affected. The fingerprint algorithm changed (v1 to v2, length-prefixed) and the history records it from now on, so a fingerprint saved by an earlier build never matches; there is no command yet that re-runs an assessment and compares it with a recorded one (`governance history` shows the fingerprints, nothing verifies them). `.governance/history/` and `.governance/reports/` are excluded from the fingerprint by path, so a change to a file there is invisible to it. Reproducibility tests normalise wall-clock fields (`generatedAt`, `assessmentId`, `evaluatedAt`, `generated_at`, `duration_ms`); verification tools that report different results over time (an advisory database, a scanner version) are outside what they prove. | Evidence can outlive a change to a file the fingerprint does not read; a recorded decision cannot yet be mechanically re-verified. | Widen the fingerprint to every tracked file (a git tree hash is the obvious source), add `governance verify <n>` to re-assess a recorded head and compare, and record tool and advisory-data versions with the evidence. |
| DEBT-GOV-021 | Audit integrity (OPS-05, ADR-0005) is a proposal and a first implementation, not a finished control. A checkpoint is a GPG signature by a key registered in the authority policy; someone who can delete the checkpoint files as well as the newest history records, with no other copy, is still undetected, and whoever holds a registered key can sign a forged history. Checkpoints are made by a person running `governance checkpoint`; nothing makes them regular, and nothing publishes them outside the repository (a signed tag, ticket or log service would). Every role in the shipped policy is DRAFT with unassigned holders and no `key_fingerprint`, so no checkpoint can verify and `require_signed_approvals` is off, until leadership names custodians. The CI history artifact continues a chain only when the history is committed in the repository, and an administrator who can edit the workflow or turn off `use_authority` can bypass recording and the policy: this needs CODEOWNERS on `.github/workflows/` and an organization ruleset that requires the governance workflow, neither of which exists. The retention periods (project life plus 7 years in git, 400 days for CI artifacts) are placeholders for leadership and legal; nothing enforces retention or prunes anything, and removing a record for legal reasons has no procedure beyond ADR-0005. Local `check` still records only with `--record`. GPG only; Sigstore and hardware-key custody are not implemented. | The history is tamper-evident against careless changes and against deletion when checkpoints survive; it is not tamper-proof against a determined insider. | Name custodians and register their keys; schedule checkpoints in CI or release; publish each checkpoint to a protected tag; add the org ruleset and CODEOWNERS; settle retention with legal; consider Sigstore. |
| DEBT-GOV-022 | Technical debt feedback (OPS-04, debt half). The pack's debt now feeds the decision (DEBT-020): P0 or P1 debt with no explicit owner blocks (sections 15 and 29), and so does any unresolved P0 debt, even if accepted (sections 9 and 17); P1 debt that is open, planned or in progress, debt past its optional `target_date`, and accepted debt with no `last_reviewed` are conditions. This is a decision change, not just reporting, and two of the choices are judgement calls the governance owner has not approved: treating every unresolved P0 as a blocker although section 29 lists only specific kinds of critical debt (the model has no debt category, so P0 stands in), and treating unresolved P1 as a condition rather than a block although section 9 says "normally blocked unless explicitly mitigated and approved" (the model has no mitigation or approver field, so ACCEPTED stands in for that decision). Not covered: debt category, origin, created date and age; "repeatedly deferred" P0/P1 debt (no history of target changes); who approved an acceptance (an ACCEPTED record is not tied to an approver or the exception process); debt linked to incidents is shown and can raise a condition (see DEBT-GOV-024), but nothing changes a debt's severity for you; and trends over time (the totals are a snapshot; the assessment history keeps them per run but nothing charts them). `owner` is free text, so any name counts, and an owner who has left is not detected. A repository's debt is only read from the pack; this repository's own register (KNOWN-DEBT.md) is a Markdown table and is not parsed. Existing packs with no `target_date` or `last_reviewed` get no overdue or review conditions. | An unowned P1 item, or any open P0, now turns a GO into a NO-GO; a project with a long untidy register will see conditions. | Owner to confirm or change the two judgement calls (the policy is in `engine/src/debt.ts`); add category, created date and approver fields; model incidents and link them to debt (OPS-04, second half). |
| DEBT-GOV-023 | `governance architecture` (the style reference, detector and suggestion) is a heuristic advisor, not a standard or a verification. Detection reads folder names, manifests and counts: it cannot tell whether dependencies follow a style, whether a `controllers/` folder is really a controller layer, or whether a style is present in name only, so a repository that copies the folder names without the discipline scores as a strong match. A folder counts only if it holds code or view templates, which removes the obvious false matches but not all. Deployables are inferred from Dockerfiles, compose services and `services/` or `apps/` folders with a manifest, so Kubernetes-only, Procfile or platform-deployed services are missed. A monorepo is assessed as one repository, not per package, so a backend in one style and a front end in another are blended; front-end structure (components, state) is not covered at all. The thresholds (40 and 300 source files, 150 for microservices) and the recommendation rules are judgement calls, not research or a governance standard, and the reference text (trade-offs, first steps) was written for this tool and has had no independent review. Nine styles omit others (CQRS and event sourcing as styles of their own, plugin or microkernel, pipeline, data-mesh). | A reader may take a heuristic suggestion as a verdict, or be told a decorative folder structure is a real architecture. | Review the catalog with the architects; detect per package in a monorepo; add dependency-direction checks to detection by reusing the profile engine; read Kubernetes and platform deployment files; calibrate the thresholds against real repositories. |
| DEBT-GOV-024 | Incident feedback (OPS-04, incident half). Incidents are recorded by hand in the pack (`incidents`), and what they feed into the decision is judgement, not a standard's wording. Every finding is a condition and none blocks: INC-019's automatic blockers (section 56) are about capabilities (incident ownership, escalation paths, recovery procedures, preserved evidence), which a list of past incidents cannot show, and the standard does not forbid a release during an active incident (section 27 even allows emergency changes), so an active P0 or P1 is a condition that says the change should be the fix. Whether an active P0 should freeze releases is the owner's decision. "Material" means P0 or P1. Repeats are found by an exact match on a free-text `cause` slug that people must tag consistently; nothing infers a root cause, so two incidents with the same cause under different slugs are not linked. The standard sets no deadline for a post-incident review, so a pending review is never "overdue". Only corrective actions on P0 to P2 incidents are checked, and the five attributes of section 36 are modelled as owner, target date and validation (priority is the incident's severity). Not modelled: the incident timeline, customer impact and communication, evidence preservation, severity reassessments, runbooks, drills and disaster-recovery exercises (sections 12, 13, 22, 41, 42, 46), and the readiness gate (section 55). The pack belongs to a repository and a change, so incidents are not shared across repositories, there is no link to an incident tracker (PagerDuty, Jira, Statuspage), and a long incident history grows the pack with no archive. Mean time to resolve is a plain mean of recorded times. | A project can look clean because nobody recorded its incidents; a repeat is missed if its cause is tagged differently. | Owner to confirm that incidents stay conditions; import incidents from a tracker; infer repeats from the affected service and alert as well as the tag; model the timeline and reassessments; keep incidents outside the per-change pack. |
