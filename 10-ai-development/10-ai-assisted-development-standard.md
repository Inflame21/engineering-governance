# AI-010 — AI-Assisted Development Standard

**Status:** Published  
**Standard ID:** AI-010  
**Applies to:** All software projects, repositories, engineers, agents, and AI-assisted development workflows governed by this framework.

---

## 1. Purpose

AI-010 defines the engineering controls required when artificial intelligence is used to analyze requirements, design systems, generate code, modify repositories, create tests, operate development tools, generate documentation, or perform other engineering work.

AI can materially increase implementation speed and breadth. It can also amplify incorrect assumptions, stale context, hallucinated APIs, insecure patterns, architectural drift, and defects across large portions of a codebase.

This standard exists to ensure that AI-assisted development increases engineering leverage without weakening engineering accountability.

> **AI may accelerate implementation, but it does not become an authority on requirements, architecture, security, correctness, or production readiness.**

---

## 2. Scope

This standard applies when AI is used for:

- requirements analysis
- technical design
- architecture proposals
- code generation
- code modification
- refactoring
- debugging
- test generation
- migration generation
- infrastructure or CI configuration
- documentation generation
- dependency selection
- API/library discovery
- repository analysis
- code review assistance
- autonomous or agentic development
- release or operational assistance
- data transformation
- any other activity that can materially affect software behavior

It applies regardless of whether AI is used through:

- an IDE assistant
- a chat interface
- a coding agent
- an API
- a local model
- a hosted model
- an autonomous workflow
- an internal AI platform
- a third-party AI service

---

## 3. Governance Position

AI-generated output is an engineering proposal until verified.

The person or team responsible for the resulting system remains accountable for:

- correctness
- security
- architecture
- requirements compliance
- data integrity
- operational behavior
- maintainability
- licensing and dependency decisions
- production readiness

AI usage does not transfer accountability to:

- the model provider
- the model
- the IDE
- the coding agent
- the prompt author
- the generated code
- another engineer who supplied context

> **The engineer who approves the change owns the consequences of the change.**

---

## 4. AI Usage Risk Classification

AI work SHALL be classified according to its potential impact.

| Level | AI Activity | Minimum Control |
|---|---|---|
| A0 | Formatting, wording, comments, low-risk transformation | Human review |
| A1 | Local implementation, refactoring, tests, documentation | Verification + code review |
| A2 | Business logic, API behavior, persistence, auth, integrations | Evidence + targeted review |
| A3 | Security controls, migrations, infrastructure, CI/CD, authorization, production operations | Explicit human approval + validation |
| A4 | Autonomous production-impacting actions | Explicit authorization, bounded permissions, auditability, rollback |

Risk classification is based on the **resulting impact**, not the apparent simplicity of the prompt.

A one-line AI-generated permission change may be A3 even if the code change is small.

---

## 5. Human Accountability

AI-generated work SHALL have an identifiable human owner.

The owner is responsible for understanding the change sufficiently to explain:

- what changed
- why it changed
- which requirements it satisfies
- which assumptions were made
- which risks were introduced
- how the implementation was verified
- how failure is handled
- how the change can be rolled back

An engineer SHALL NOT approve code solely because:

- the model generated it confidently
- another model reviewed it
- tests generated by the same model pass
- the IDE reports no errors
- the implementation looks idiomatic
- the generated explanation sounds reasonable

---

## 6. Source-of-Truth Hierarchy

AI systems frequently receive conflicting context. The development workflow SHALL define authoritative sources.

Recommended precedence:

1. Approved business requirements
2. Approved security requirements and constraints
3. Approved architecture and ADRs
4. Approved API/data contracts
5. Current source code and schema
6. Approved tests and acceptance criteria
7. Current engineering standards
8. Current operational documentation
9. User-provided task context
10. AI-generated suggestions

Lower-level AI output SHALL NOT silently override a higher-authority artifact.

If authoritative sources conflict, implementation SHALL stop until the conflict is resolved.

---

## 7. Context Governance

### 7.1 Context Is an Engineering Input

AI context SHALL be treated as an engineering input, not conversational decoration.

Incorrect, stale, contradictory, duplicated, or irrelevant context can produce systematically incorrect software.

> **Bad context can produce consistently wrong code at high speed.**

### 7.2 Context Quality

Before substantial AI-assisted implementation, verify that relevant context is:

- current
- authoritative
- internally consistent
- scoped to the task
- free of obsolete instructions
- free of unrelated implementation history
- explicit about constraints
- explicit about non-goals
- traceable to source artifacts where practical

### 7.3 Context Contamination

The following SHALL be treated as context contamination:

- obsolete architecture instructions
- superseded requirements
- contradictory coding rules
- old API contracts
- abandoned implementation plans
- unrelated project history
- stale generated documentation
- duplicated instructions with conflicting priorities
- assumptions presented as facts
- examples that no longer match production behavior

Contaminated context SHALL be removed, corrected, or explicitly superseded before relying on AI output.

### 7.4 Context Boundaries

AI sessions SHALL use the smallest context necessary to perform the task correctly.

Do not provide an entire repository when the task requires only:

- a module
- an interface
- an API contract
- a specific workflow
- a bounded set of files

Broad context is justified when the task genuinely requires system-level reasoning.

### 7.5 Context Versioning

For high-risk or long-running AI-assisted work, important context SHOULD be versioned alongside the relevant engineering artifacts.

Examples include:

- architecture documents
- ADRs
- implementation plans
- domain constraints
- API contracts
- database contracts
- AI agent instructions

AI instructions SHALL NOT become an undocumented shadow architecture.

---

## 8. Prompt and Task Hygiene

AI tasks SHALL be explicit about:

- objective
- scope
- constraints
- authoritative references
- expected behavior
- non-goals
- acceptance criteria
- files or modules in scope
- prohibited changes
- required validation

For complex changes, the task SHOULD be decomposed into bounded steps.

Avoid prompts such as:

> "Build the entire feature however you think is best."

Prefer:

> "Implement the approved behavior in module X according to requirement Y and ADR Z. Do not change persistence or authentication. Add tests for the listed acceptance criteria."

The second form creates a bounded engineering problem.

---

## 9. AI-Generated Code Verification

Every material AI-generated implementation SHALL be verified against:

1. requirements
2. architecture
3. existing contracts
4. domain invariants
5. security constraints
6. error behavior
7. concurrency behavior
8. data integrity requirements
9. tests
10. operational expectations

Verification SHALL examine the resulting behavior, not merely the generated explanation.

### Required Questions

- Does the code solve the actual requirement?
- Does it preserve existing invariants?
- Does it belong in this architectural layer?
- Does it introduce hidden coupling?
- Does it alter public behavior?
- Does it introduce new failure modes?
- Does it handle invalid input?
- Does it handle partial failure?
- Does it handle retries?
- Does it handle concurrency?
- Does it preserve authorization boundaries?
- Does it expose sensitive information?
- Does it create an operational burden?
- Can a human maintainer understand it?

---

## 10. AI-Generated Tests

AI-generated tests SHALL NOT be treated as independent evidence when the same assumptions generated both the implementation and the tests.

Reviewers SHALL determine whether tests actually challenge the implementation.

AI-generated tests SHOULD include, where relevant:

- happy paths
- invalid input
- authorization failures
- boundary conditions
- state transitions
- concurrency
- retries
- duplicate requests
- partial failures
- dependency failures
- persistence failures
- recovery behavior
- regression cases

A high number of AI-generated tests does not compensate for weak test design.

---

## 11. Architecture and ADR Governance

AI may propose architecture, but approved architecture remains authoritative.

AI-generated architectural decisions SHALL NOT be adopted implicitly.

When AI proposes a material architectural change, the team SHALL evaluate:

- requirements impact
- domain boundaries
- dependency direction
- data ownership
- runtime behavior
- failure modes
- scalability
- security
- operational complexity
- migration cost
- reversibility

If the decision changes an architectural constraint, an ADR or equivalent decision record SHALL be updated.

> **Generated architecture is not approved architecture.**

---

## 12. Dependency and API Hallucination Controls

AI frequently produces plausible but nonexistent or incorrect:

- packages
- functions
- framework APIs
- configuration options
- CLI commands
- SDK methods
- database features
- provider capabilities

Any externally sourced API, package, framework feature, or configuration SHALL be verified against an authoritative source before production use.

Verification SHOULD use:

- official documentation
- installed package metadata
- source code
- lockfiles
- generated API specifications
- compiler/type checker
- runtime verification
- reproducible tests

A generated dependency SHALL NOT be added merely because the model claims it exists.

---

## 13. Dependency Governance

AI recommendations for dependencies SHALL be evaluated using the same criteria as human recommendations:

- maintenance status
- license
- security history
- transitive dependency impact
- compatibility
- release maturity
- operational burden
- community or vendor support
- bundle/runtime impact
- necessity

Prefer existing approved dependencies when they satisfy the requirement.

AI SHALL NOT be used as justification for dependency proliferation.

---

## 14. Security and Privacy

AI-assisted development SHALL comply with SEC-007.

### 14.1 Sensitive Data

Do not provide external AI systems with sensitive information unless explicitly authorized.

This includes, where applicable:

- credentials
- access tokens
- private keys
- session secrets
- production secrets
- personal data
- customer data
- regulated data
- confidential business information
- proprietary source code
- private infrastructure details

Redaction or synthetic data SHALL be used where possible.

### 14.2 Secret Handling

Secrets SHALL NOT be placed in:

- prompts
- agent instructions
- committed AI transcripts
- generated source code
- generated configuration
- issue comments
- documentation

### 14.3 Security Reasoning

AI-generated security controls require human verification.

This includes:

- authentication
- authorization
- cryptography
- token handling
- input validation
- file handling
- tenant isolation
- security headers
- CORS
- CSRF protection
- rate limiting
- secrets handling

Security-sensitive generated code SHALL be treated as A3 risk.

---

## 15. AI-Specific Threat Model

Teams using AI-assisted development SHOULD consider:

| Threat | Example | Control |
|---|---|---|
| Context poisoning | Stale instruction causes wrong architecture | Source-of-truth hierarchy |
| Prompt injection | Repository content manipulates an agent | Treat repository data as untrusted input |
| Tool abuse | Agent executes destructive command | Least privilege + command boundaries |
| Hallucination | Nonexistent API is implemented | Authoritative verification |
| Data leakage | Secrets sent to provider | Data classification + redaction |
| Scope drift | Agent modifies unrelated modules | Explicit task boundaries |
| Silent architecture drift | Generated code bypasses approved boundaries | Architecture review |
| Test illusion | Generated tests validate generated assumptions | Independent test review |
| Dependency risk | AI adds unnecessary package | Dependency governance |
| Stale context | Agent follows superseded rules | Context freshness checks |

---

## 16. Agentic Development and Tool Permissions

Autonomous agents SHALL operate under least privilege.

Permissions SHOULD be separated by risk.

### Read permissions

Generally lower risk:

- source inspection
- documentation inspection
- test inspection
- static analysis

### Write permissions

Require stronger controls:

- source modification
- test modification
- configuration modification
- dependency changes

### High-risk permissions

Require explicit authorization:

- database migrations
- production configuration
- infrastructure changes
- CI/CD changes
- credential access
- destructive commands
- deployment
- data deletion
- production mutations

Agents SHALL NOT receive unrestricted production credentials merely to simplify development.

---

## 17. Command and Tool Safety

AI agents SHALL NOT be trusted to infer whether a command is safe.

High-risk commands SHOULD require explicit human confirmation or a controlled execution environment.

Examples include:

- recursive deletion
- database destruction
- production migrations
- credential rotation
- infrastructure destruction
- force pushes
- rewriting shared history
- bulk data modification
- production deployment

Use:

- sandboxing
- scoped credentials
- temporary environments
- dry runs
- approval gates
- allowlists
- audit logs
- rollback mechanisms

where appropriate.

---

## 18. Database and Migration Changes

AI-generated schema and migration changes require heightened review.

Review SHALL verify:

- schema correctness
- constraints
- indexes
- foreign keys
- nullability
- default behavior
- transaction semantics
- locking behavior
- backward compatibility
- expand/contract strategy
- data preservation
- rollback feasibility
- production execution time

An AI-generated migration SHALL NOT be applied to production solely because it succeeds in a development database.

---

## 19. Infrastructure and CI/CD Changes

AI-generated changes to infrastructure, deployment configuration, IAM, networking, containers, CI/CD, or environment configuration SHALL be treated as high-risk.

Review SHALL include:

- permissions
- secrets
- network exposure
- environment separation
- deployment behavior
- rollback
- failure behavior
- resource limits
- cost implications
- drift risk
- auditability

These changes normally require explicit human approval before execution.

---

## 20. Documentation Generated by AI

AI-generated documentation SHALL be verified against the actual system.

Documentation SHALL NOT be considered authoritative merely because it is:

- detailed
- internally consistent
- professionally written
- generated from source code
- reviewed by another AI

Verify:

- commands
- APIs
- configuration
- architecture
- behavior
- examples
- operational procedures
- failure/recovery instructions

Incorrect documentation is an operational defect.

---

## 21. Code Provenance and Traceability

For high-risk AI-assisted changes, teams SHOULD retain enough information to reconstruct:

- what was requested
- which authoritative artifacts were used
- what the AI changed
- what was manually changed
- how the result was verified

The objective is not to preserve every conversation.

The objective is to preserve engineering evidence for material decisions.

Where repository policy requires attribution or disclosure of AI-assisted work, it SHALL be followed.

---

## 22. Human-in-the-Loop Controls

Human review is mandatory when AI output can materially affect:

- security
- authorization
- sensitive data
- database integrity
- architecture
- public API behavior
- infrastructure
- CI/CD
- production configuration
- financial behavior
- compliance behavior
- destructive operations

The higher the impact, the more independent the verification should be.

---

## 23. AI-Assisted Code Review

AI may assist code review but SHALL NOT replace accountable human review where human review is required by REV-009.

AI review can be useful for:

- identifying suspicious patterns
- finding repetitive defects
- suggesting test cases
- spotting missing error handling
- summarizing diffs
- detecting obvious inconsistencies

AI review is insufficient evidence for:

- production approval
- security approval
- architecture approval
- final correctness
- risk acceptance

> **AI can be a reviewer assistant. It is not the production approver.**

---

## 24. Evidence Requirements

For material AI-assisted work, evidence SHOULD include:

- requirement or issue reference
- architecture/ADR reference where applicable
- relevant tests
- validation results
- security validation where applicable
- migration validation where applicable
- review outcome
- unresolved risks
- rollback considerations

Evidence SHALL demonstrate behavior rather than merely stating that AI was used.

---

## 25. AI Quality Gate

Before production approval, the reviewer SHALL confirm:

### Requirements

- [ ] The implementation maps to approved requirements.
- [ ] AI-generated assumptions were identified and verified.
- [ ] Scope did not silently expand.

### Architecture

- [ ] Approved architecture is preserved.
- [ ] Architectural changes were explicitly reviewed.
- [ ] New dependencies and coupling are justified.

### Code

- [ ] Generated code is understandable.
- [ ] Business logic is in the correct layer.
- [ ] Error and failure behavior is intentional.
- [ ] No obvious hallucinated APIs or assumptions remain.

### Security

- [ ] No secrets or sensitive data were improperly exposed.
- [ ] Authentication and authorization are correct.
- [ ] AI-generated security controls were independently verified.
- [ ] Tenant/data isolation remains intact where applicable.

### Testing

- [ ] Tests provide meaningful behavioral evidence.
- [ ] Negative and failure paths are covered where relevant.
- [ ] Tests are not merely copies of implementation assumptions.
- [ ] Required CI checks pass.

### Operations

- [ ] Logging and observability are adequate.
- [ ] Migrations and deployment behavior are understood.
- [ ] Rollback/recovery is defined for material changes.

### Context

- [ ] Relevant AI context was current.
- [ ] Contradictory or obsolete instructions were removed.
- [ ] The authoritative source hierarchy was respected.

---

## 26. Automatic Production Blockers

AI-assisted work SHALL NOT receive production approval when:

- AI-generated code contains unresolved critical defects.
- AI output contradicts approved requirements.
- AI output violates an approved architecture constraint without review.
- Generated dependencies or APIs remain unverified.
- Security-sensitive generated behavior has not been independently validated.
- Production-impacting agent actions lack appropriate authorization.
- Secrets or sensitive data were improperly exposed.
- Generated migrations have not been adequately validated.
- AI-generated tests are the only evidence for a material behavior and lack independent review.
- Context contains unresolved contradictory authoritative instructions.
- The reviewer cannot explain the material behavior of the resulting implementation.
- Required human approval has been bypassed.
- AI-generated infrastructure changes lack adequate operational validation.
- A production-impacting autonomous workflow has no bounded permissions or rollback strategy.

---

## 27. Review Decision

AI-assisted work SHALL follow the same production decisions defined by the governance framework:

### GO

Requirements, architecture, implementation, security, testing, and operational evidence are sufficient.

### GO WITH CONDITIONS

Known P2/P3 risks remain and are explicitly accepted with owners and deadlines.

### NO-GO

A P0/P1 issue, insufficient evidence, unresolved architectural conflict, security risk, or other production blocker remains.

AI usage itself is neither a reason to approve nor a reason to reject a change.

---

## 28. AI Development Anti-Patterns

The following are prohibited or strongly discouraged:

### "Vibe coding" without verification

Generating large amounts of code and assuming it works because the application runs.

### Prompt-driven architecture

Allowing an AI response to silently become the system architecture.

### Context dumping

Providing massive amounts of stale or unrelated context instead of curated authoritative context.

### AI-to-AI approval loops

Using one model to generate code and another model to approve it without accountable human verification.

### Generated-test illusion

Treating generated tests as independent proof when they were derived from the same generated assumptions.

### Hallucinated dependency adoption

Adding a package or API because an AI model claimed it exists.

### Autonomous production mutation

Allowing an agent to make production-impacting changes without bounded permissions and approval.

### Blind refactoring

Accepting broad AI refactors without understanding the changed behavior and blast radius.

### Documentation hallucination

Publishing generated documentation without verifying it against the actual system.

### Secret exposure

Sending secrets, credentials, or unauthorized sensitive data to an AI system.

### Context-as-truth

Treating model context as authoritative when it conflicts with requirements, architecture, code, or contracts.

## 30. Change Control

Changes to AI-assisted development practices SHALL follow the same governance model as other engineering standards.

Changes that materially affect:

- AI permissions
- autonomous execution
- data handling
- security controls
- production approval
- context governance
- auditability

SHALL be explicitly documented and reviewed.

---

## 31. Exceptions

Exceptions to AI-010 require an explicit engineering exception under EXC-021.

The exception SHALL document:

- requested deviation
- reason
- affected systems
- risk
- compensating controls
- owner
- expiration/review date

AI convenience is not sufficient justification for an exception.

## 34. Final Principle

> **AI is an implementation accelerator, not an engineering authority.**

The objective of AI-assisted development is not to maximize generated code.

The objective is to maximize engineering throughput **without reducing correctness, security, maintainability, accountability, or production confidence**.

**Generate quickly. Verify deliberately. Approve responsibly.**
